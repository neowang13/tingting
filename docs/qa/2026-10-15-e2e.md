## Issue fixed during QA

Client login could submit natively before React attached its event handler. The browser's default GET submission put form values into the URL and lost the application return path. Login forms and client signup now use a POST fallback and keep their submit button disabled until hydration attaches the handler. Client login, admin login, and signup each have a no-JavaScript regression test. Authentication rules and rate limits remain enforced.

Test isolation was also corrected: showing tests now use a separate synthetic client IP per test instead of exhausting the login limit across the suite. The live application test creates a fresh application for the second demo property, avoiding the fixed seeded application's ID colliding with Resend's idempotency protection across repeated memory-server restarts. Navigation and uploads are checked only after their corresponding URL/response is available.

## Supabase deployment blocker

A read-only schema inspection of the configured Supabase project found:

- `property_viewing_schedules` is absent. A direct zero-row table query returned HTTP **404**, error **PGRST205**.
- `save_property_viewing_draft` is absent.
- `publish_rental_with_viewing_dates` is absent.
- Existing application, applicant, notification-outbox resources and the older reservation function exist; their presence does not validate the new migrations or RLS behavior.

At least migrations `202610150060_property_viewing_dates_and_users.sql` and `202610150061_unified_property_publication.sql` have not been applied. Before deploying this complete feature set, validate and apply the documented `060–063` migration sequence against the intended database, then run the isolated Supabase E2E and SQL/RLS checks. No production database schema or applicant records were modified by this QA run. This report does not certify production readiness.

## Re-run

Ordinary browser tests use a separate local instance:

```sh
corepack pnpm exec playwright test --config=playwright.qa.config.ts
```

The live email suite requires explicit authorization and a designated recipient:

```sh
E2E_LIVE_EMAIL_CONFIRMED=true E2E_EMAIL_RECIPIENT=info@silverkey.ca corepack pnpm exec playwright test --config=playwright.email.config.ts
```

The live suite loads email credentials from `.env.local`, writes only memory-backed application data, and sends real test emails. It does not test Supabase persistence, real signup verification, SMS delivery, or production deployment. Never substitute an unapproved recipient.
